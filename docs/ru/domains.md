# Перенос продукта в домен

Правила — `DOM-01`–`DOM-03`. Здесь — порядок работы.

## Карта

`docs/domain-map.md` в приложении перечисляет продукты, которые ещё живут
вне `app/Domain/<Продукт>`:

| Столбец | Смысл |
| --- | --- |
| Продукт | Имя, которым его называет дело |
| Сейчас | Каталоги сегодня |
| Цель | `app/Domain/<Продукт>` |
| Зависит от | Другие продукты, которые надо перенести раньше, или «нет» |
| Риск | Что заметит вызывающий, если перенос сделан неверно |

Шаблон — `templates/domain-map.md`. Одна строка — одна задача. Задача на
функцию забирает перенос, только если она и так переписывает этот продукт.

Новый продукт на карту как будущий перенос не попадает. Его сразу создают
в `app/Domain/<Продукт>` (`DOM-02`). Новую внешнюю систему создают в
`app/Integrations/<Система>`.

## Порядок одного переноса

1. Согласовать строку. Паспорт остаётся на текущем каркасе, пока перенос
   не закончен. Перенос не переводит старое приложение на базовые классы
   handbook и не переводит приложение handbook на контроллеры forge, если
   ADR этого не говорит.
2. Добавить characterization-тесты на поведение, которого коснётся перенос
   (`recipes/characterization-test.md`). Они зелёные до перемещения файлов.
3. Перенести код. Публичные HTTP-пути, имена классов в очереди (`JOB-02`),
   команды планировщика и ключи конфигурации остаются или получают псевдоним.
4. Добавить архитектурный тест: домен не лезет во внутренности другого
   продукта, а формат внешней системы знает только
   `app/Integrations/<Система>`.
5. Покрытие перенесённого домена с этого момента — `TEST-01`. Остальное
   приложение остаётся на `TEST-02`, пока не переедет.

## Чего перенос не включает

Обновление PHP, смену СУБД, смену форматера и новый пакет админки. Каждое
из этого — своя задача, а для СУБД ещё и ADR (`DB-01`).
