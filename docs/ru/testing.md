# Тесты

Тесты — часть изменения, а не следующая задача. Они идут на той же СУБД и
той же основной версии, что и production (`DB-01`). SQLite запрещён.

Новое приложение и домен после `DOM-01` закрывают `TEST-01`: 80% строк
проектного PHP и 70% строк интерфейса, в котором есть логика. Старое
приложение закрывает `TEST-02`: около 70% строк, которые меняет запрос на
слияние, и общее покрытие репозитория не падает. Команду для diff записывает
паспорт. Сквозные тесты в эти проценты не входят (`e2e.md`).

## Сервер

Новый проект и проект каркаса handbook используют Pest (`PHP-06`). Проект,
который уже на PHPUnit, остаётся на нём. Новые тесты PHPUnit пишут с
атрибутом `#[Test]` и именами методов в `snake_case`.

Функциональные тесты используют `RefreshDatabase`. Данные — из фабрик.
Почта, HTTP, очереди и уведомления — подмены. Тест сам готовит своё
состояние.

```php
<?php

declare(strict_types=1);

describe('project archive', function () {
    it('hides an archived project from the default list', function () {
        $project = Project::factory()->create(['archived_at' => now()]);

        $this->actingAs($this->viewer())
            ->getJson('/api/v1/projects/list')
            ->assertOk()
            ->assertJsonPath('success', true)
            ->assertJsonMissing(['id' => $project->id]);
    });
});
```

Имена в Pest — английские предложения. Имя метода PHPUnit — `snake_case`
(`PHP-06`). Один тест — одно поведение. Хотя бы одно утверждение. `sleep` не используют. Время двигают через
`Carbon::setTestNow()`. Приватный метод не вызывают: проверяют публичное
поведение.

Минимум для новой точки API: успешный путь, ошибка валидации и отказ в
правах. У политики есть разрешение и отказ. У действия есть тест на исход,
который оно обещает.

Не тестируют `save` у Eloquent, миграцию, файл конфигурации и чужой пакет.
Экран Orchid проверяют только на права.

Порог 80% строк — это `TEST-01`: новое приложение и домен после переноса.
Старое приложение вместо этого порога следует `TEST-02`. В покрытие входит
`app/`. Заготовки фреймворка, которые проект не менял, можно исключить, с
комментарием, что это заготовки. Как только файл меняют, исключение
снимают. `bootstrap/`, `config/`, `routes/` и `database/` в процент не
входят. Процент не снижают, чтобы изменение прошло.

## Фронтенд

Vitest и Vue Test Utils. Тесты лежат там, где проект их уже кладёт
(`frontend/tests/` или `src/**/__tests__/`). Покрывают компонент с логикой,
composable и клиент API. Оформительская обёртка над компонентом набора
целью покрытия не является.

70% интерфейса с логикой — порог `TEST-01`. Старое приложение на изменённых
строках запроса следует `TEST-02`.

Клиент API проверяют с подменённым `fetch` или Axios, не с живым сервером.
Проверяют форму ответа, которую использует проект (конверт или ресурс
API), заголовок CSRF на записи и тип ошибки.

## Статический анализ и формат

Изменение не готово, пока для затронутых языков не прошли:

- форматер проекта (`PHP-02`): `vendor/bin/pint --test`, если проект на
  Pint, и phpcs, если он всё ещё на phpcs
- Larastan на уровне проекта (`max` у нового приложения)
- `vue-tsc --noEmit`
- скрипт ESLint проекта

Перед изменением поведения, у которого нет теста, текущее поведение
фиксируют characterization-тестом (`recipes/characterization-test.md` в
корне пакета).

## Условия слияния

Проверка из паспорта, которая не выполнилась, — это провал. Сквозные тесты
в этот список не входят (`E2E-03`). Не ставят `allow_failure`, не
дописывают `|| true` и не передают `--ignore-unreachable` в
`composer audit`. Нестабильный тест чинят до следующей задачи, а не
перезапускают, пока он случайно не станет зелёным.

Условие слияния — пайплайн запроса на слияние, а не пайплайн ветки, на
который никто не смотрит. Изменение только в документах может пропустить
проверки кода. Проверку защиты данных пропустить нельзя.
